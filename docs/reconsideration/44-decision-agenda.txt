LOCALSWIM: FRESH-CHOICE ARCHITECTURE DECISION AGENDA (#0044)
2026-10-25 | Primary synthesis | Recommendations, not a replacement baseline

Outcome
Use working v1 to identify valuable jobs and observable behavior. Require a case
for every retained mechanism and every departure. Earlier v2 approval gives a
candidate no immunity. This reassessment supports significant simplification,
but neither an exact clone nor a universal "perfect" stack has been established.
Public MIT FOSS, private operational data and UTF-8/LF remain standing commitments.

The strongest provisional system is a compact local application: one authoritative
domain core, browser and CLI adapters, transactional board storage with readable
exports, explicit user priority, and optional publishing/delivery outside saves.
Go plus TypeScript remains a credible implementation; language, UI composition,
transport and process placement stay conditional on combined evidence below.
This is a proposed direction, not approval to replace the earlier architecture.

What genuinely changes the design
Storage is the clearest mechanism challenge: JSON was buying readable authority
and Git diffs while requiring a custom transaction/recovery protocol. A database
is attractive if that trade removes more correctness machinery than it adds.
It still leaves authorization, uncertain responses and external-byte safety to us.

Priority is the clearest domain challenge: a user's chosen urgency, whether work
can start, and influence on other work are different facts. Permanently changing
one because another changed needs demonstrated value. Imported priorities cannot
be demoted automatically: their original intent is unknown.

Security is the largest requirement-dependent decision. Calling a launcher human
does not exclude automation with the same account powers. Stronger exclusion must
also protect authoritative state/policy. Extra certificates, origins or processes
cannot substitute for choosing and testing that assurance boundary. Stable versus
new-per-instance origins also trade browser continuity against fencing obligations.

Recovery is a product choice as well as storage engineering. Restoring unsent
prose must not turn an unresolved submitted comment into a fresh submission. Lost
or expired operation evidence remains unknown; reauthentication and reload never
authorize automatic replay.46's proposed private record has a real cost that must
be judged alongside privacy and browser availability.

Smallest useful next decision cycle
First select essential daily journeys, initial real platform, history/draft loss
tolerance and approval assurance. Record continuity, improvement, intentional loss,
cost and acceptance example for each disputed boundary. This is one concise ledger,
not a new approval layer for ordinary engineering details.

Then consider a separately authorized, disposable comparison.46 proposes a
two-maintainer-day ceiling across candidates; that is an effort hypothesis, not
permission or a promise to finish. Couple language packaging with representative
SQLite bindings, equivalent engine/features, the same attachment placement and
protected backup scope. If placement is disputed, compare it symmetrically.
Combine conflict/restart/reconciliation, reload, partial workspace outage, stopped
inspection and delivery interruption where practical. Stop at the effort cap and
record partial evidence rather than build the entire proposed baseline.

Decide from observed user losses, operating steps, implementation mechanisms and
maintainer effort. Broader qualification follows the selected release slice.
Migration, trust installation and cutover require their own scope; v1 can continue
serving real work throughout. New recommendations remain RFR for Terry's choice;
no prior card is reopened or quietly superseded as an adopted design.
