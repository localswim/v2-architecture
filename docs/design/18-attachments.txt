Identity and mutability
Recommend immutable board-local byte objects, identified by opaque object identity
plus algorithm-tagged SHA-256 digest and exact byte length. Attachment identity is
distinct: each committed attachment associates a card with one verified object.
Equal bytes need not merge attachment identities. No cross-board deduplication or
existence disclosure. Never overwrite an object with changed content; replacement
requires new bytes and an explicit manifest mutation. Verify an existing object's
length/digest before reuse; mismatch quarantines it.

This independently selected option simplifies10's forbidden incomplete references:
bytes become complete first; one JSON replacement commits references and audit.
It does not inherit a source layout. Mutable files are an alternative requiring
versioned replacement and preservation of every referenced revision; in-place
overwrite cannot satisfy retained-snapshot integrity. Immutable storage costs
retained capacity and requires explicit retention policy.

Metadata, names and covers
The canonical board manifest owns attachment/card/object association, original
display name, declared versus verified media classification, size/digest and cover
selection. Go authorizes metadata edits and atomically co-commits attributable
audit/operation outcomes. Audit records attachment identities and action/revision,
not payloads or full filename prose. Refusals and staging failures produce sanitized
diagnostics, not successful-change history.

Original names are bounded untrusted display text: escape controls/markup and
provide a safe download-name fallback. They never select storage paths or commands.
Use opaque generated storage names beneath the owned aggregate. Reject traversal,
absolute/drive/UNC paths, unsafe links/reparse points and races; qualify containment
at opening/use, not string-prefix comparison. Covers reference a current authorized,
preview-eligible attachment on that card. Removing that attachment atomically clears
its cover; no unrelated replacement is chosen.

Upload and outcome contract
Authenticate transfer initiation, byte access and finalization separately; board
ownership is not workspace-wide authority. Enforce advertised per-file/request,
aggregate capacity, concurrent-transfer, streaming/decode, filename and deadline
bounds before and during receipt. Reserve capacity, reject dishonest length and
incomplete/excess streams, compute digest while receiving, then verify complete
stored bytes. Numerical budgets remain unqualified specification work.

Session-bound browser headers/cookies/origin checks follow32; sessions never define
operation identity. The manifest command identity is scoped to stable principal
and aggregate, independent of session/host generation. Its fingerprint includes
command/version, board/card target, object digest/length, metadata and all expected
revision/evidence preconditions. Transfer handles are opaque, principal/board/
operation-scoped staging locators, not bearer authority or commit evidence.
Switching boards must not redirect late responses; clients retain target and
operation correlation plus separate diagnostic request identity.

Stage, close/flush and make complete verified objects available before the manifest
replacement. Reauthorize and recheck board/policy/card fences immediately before
commit. Serialize matching operations and follow32's recognition rules; a retained
match returns its historical outcome, mismatch conflicts, absent retry evidence
is indeterminate. A lost response cannot authorize upload restart or new mutation.

Delivery and publisher boundary
Authorize every preview/download against explicit board/attachment and current
rights. Deliver originals as inert downloads with safe headers/names; never render
uploaded HTML/SVG/scripts in the trusted application origin. Generate bounded raster
previews with an allowlisted decoder and verified source digest; previews are
disposable derivatives, never authoritative replacement bytes.
