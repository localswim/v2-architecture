LOCALSWIM REBOOT — QUALITY ATTRIBUTES (#0003)
Candidate foundation note, 2026-10-25; subject to #0004 and Terry's acceptance.

Authority and evidence
Hard user constraints: new Go core/service/CLI/background tools and TypeScript 7.x browser; clean-room architecture work only; no implementation, migration or cutover. Existing Python services and boards remain independent. This note grants no compatibility promise or permission to read legacy implementation. Foundation cards are parallel candidates, not an accepted baseline.

Sources: architecture-input-brief-r2.txt; cards-r2/0003-arch-quality-attributes.txt; C:/Projects/localswim/README.md, only the permitted sections Multiple boards in one workspace, Board configuration, Daily use, Archiving cards, Card attachments and cover photos, Dependency priority inheritance, Transition permissions, Data safety and Git, Shared board-write monitor. Public behavior documentation was read from the local README, not independently verified against a release.

Recommended operating envelope
Prioritize a single-user desktop installation on Windows 11 x64, with multiple browser windows and automation/CLI actors. Recommend Linux x64 as the second validation platform; defer macOS, ARM, containers and remote multi-user hosting until owner demand justifies their release matrix. These are proposed platforms, not discovered deployment facts. Browser acceptance should cover the stable Edge, Chrome and Firefox versions selected at test freeze; browser/toolchain versions require separate verification. TS7 release/channel policy remains #0022's decision.

Recommend loopback-only service exposure and local storage on a directly attached filesystem. Internet and Git should be optional for ordinary reads/writes; offline startup must use bundled assets. Exclude network shares, cloud-synchronized live storage and hostile local-machine isolation from the initial guarantee pending separate decisions. Loopback does not itself authenticate actors: authorization and request-origin protection remain design requirements.

Proposed reference workload, unverified: 4 CPU cores, 8 GiB RAM, SSD; 20 discovered boards, 5,000 cards per active board including archived cards, 50,000 relationships, 20 MiB serialized structured state, 100 MiB individual attachments, 2 GiB retained attachment bytes per board, 4 browser windows and 2 CLI clients. Exercise a 10-mutation/second burst for 10 seconds and 1/second sustained for 10 minutes. Attachment bytes must not be included in full-board response bodies. These provisional ceilings replace no existing limits; storage feasibility needs later validation. Use synthetic fixtures, never private boards. Measure locally with Git disabled unless specified; report dataset, OS, browser and sample count.

Proposed quality scenarios (all targets, no measurements)
1. Concurrent edits: two clients submit changes against one revision. Exactly one conflicting transaction succeeds; the other receives an explicit conflict without lost updates or blind replay. Across 1,000 synchronized trials, every accepted edit appears once in state and audit.
2. Ambiguous response: disconnect after submitting a mutation. UI/CLI reports an unknown outcome and provides reconciliation guidance within 5 seconds of detecting failure; reconnect never automatically duplicates the edit. Draft input survives until reconciliation or explicit dismissal.
3. Malformed state: introduce invalid syntax, invalid references or unsupported format in a synthetic fixture. Refuse mutation and expose an actionable sanitized diagnostic within 5 seconds; original bytes remain unchanged. One faulty board does not prevent opening a healthy board.
4. Process failure: interrupt each persistence boundary in a synthetic fault campaign. Restart within 10 seconds exposes a fully valid pre-transaction or committed state, never partial state; acknowledged local saves survive process termination. Attachment metadata never points to incomplete bytes; uncertain orphan bytes are preserved for recovery. Power-loss survival remains unqualified pending storage decisions.
5. Disconnected Git: reject remote operations for 10 minutes while editing. Local saves continue within ordinary budgets; visible local-save and publish states remain distinct. Publishing retries without duplicate user edits; unrelated repository files remain untouched in every fixture.
6. Large board: at the reference envelope, first interactive board view completes within 3 seconds and search responds within 300 ms at p95 over 100 operations after warm-up. Browsing remains responsive while attachment transfer runs.
7. Write responsiveness: under the reference burst, local mutation acknowledgement is p95 <=500 ms and p99 <=2 seconds across at least 1,000 requests; conflicts are reported separately. Whole service working set remains <=512 MiB, excluding OS caches; excess load fails visibly without corrupting state.
8. Workspace navigation: 100 board switches and Back/Forward cycles preserve each window's drafts, selection and focus. Healthy board switching is p95 <=1 second when warm. Unknown bookmarks show an error and never substitute another board.
9. Accessibility: keyboard-only users complete create, edit, move, search and attachment-download flows with visible focus and correct focus return. Automated checks plus a screen-reader walkthrough find no critical blockers; normal text contrast is >=4.5:1 and meaning never relies solely on color.
10. Observability: inject storage, authorization, conflict and publish failures. Every failure has a stable category and correlation reference; state distinguishes durable save from pending/failed publishing. Logs contain zero fixture prose, credential values or attachment payloads.
11. Monitoring: test bot-only, human, mixed, unknown, empty, malformed and failed activity queries. Suppress only nonempty proven automation-only results in every case; no filesystem-write/event-count equality assumption. Recovery preserves uncertain intervals and avoids silent alert loss.

Tradeoffs and owner decisions
Safety and honest failure states outrank latency targets. A desktop-first envelope reduces release cost; deferred platforms reduce reach. Larger state/attachment ceilings increase memory, backup and recovery costs. Require Terry to select retained capabilities, supported platforms, workload ceilings, accessibility conformance scope, backup frequency/retention and acceptable data loss after hardware failure. Recommend a verified backup/restore drill before release; its recovery-time target depends on chosen storage and backup location. These unresolved choices are downstream gates, not reasons to invent guarantees here.
