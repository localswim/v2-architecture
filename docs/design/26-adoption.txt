Coexistence and qualification
Use distinct storage roots/ownership anchors, runtime records, listeners/origins,
credentials, publication repositories/scopes and monitor lock/status/target paths.
Never point both implementations at one writable aggregate, share pending commands,
dual-write, auto-synchronize or infer safe handoff from an absent listener. Existing
Python operations continue through their shared implementation and original targets;
new tooling must not adopt them implicitly. Reserve synthetic identities to avoid
accidental cross-routing. Copying a board does not transfer physical ownership.

Qualification first uses newly authored synthetic fixtures and accepted behavior
packets under02's disclosed-provenance method. An approved source-copy rehearsal
would be a later private operation with explicit asset/evidence permission, isolated
paths and disabled external effects. Pin source revision/inventory and mapping
revision; compare counts, references, policy meaning, actor provenance and bytes.
Retain rejected evidence and a loss/unsupported-field report. A successful parse,
Git push or published compiler metadata is insufficient evidence of readiness.

Rollback conditions and residual risk
Keep the prior executable/toolchain manifest and supported API/storage/feature matrix
with each rehearsal. Binary replacement alone is rollback only when that release
can validate the current storage, policy and required features. Forward-only schema
changes require a tested restore or separately approved reverse mapping; never
point Python at new-format files. Restoring a pre-cutover copy loses subsequent
new-system changes unless explicitly reconciled. Preserve both histories and bytes;
audit metadata cannot reconstruct missing prose or reverse committed external effects.

Rollback must also prove a usable intended-instance trust path: authorized issuer
setup, protected keys, fresh hostname/key/grants/sessions and current scopes under32.
Never restore reusable credentials or bypass warnings. Controlled trust provisioning
and any trust removal remain separately authorized future actions; architecture
acceptance installed nothing. If any version, storage, ownership, backup or trust
condition is unproven, keep the affected scope fenced and require an explicit
recovery decision rather than claim rollback readiness.
