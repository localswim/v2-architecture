Recommended topology
Use one Go host per explicitly configured local hosting root. The same host supports
one standalone board or a workspace containing several boards. A workspace is a
registry and navigation view, not a shared board transaction or authorization scope.
Each board has an independent engine instance, storage handle, command queue,
revision context and health state. Opening a workspace must tolerate unavailable or
invalid boards. Bound concurrent loading, queues and attachment transfers so one
busy board cannot consume every host resource.

Use supervised Go child workers for optional monitoring and publishing. This keeps
network/Git waits and worker failures outside request handling without prescribing
one service process per board. Worker granularity follows ownership: monitoring has
one lease/cursor per board; publishing has one coordinator per repository, including
repositories containing multiple boards. Workers may serve multiple owned scopes
with bounded concurrency. Their supervision does not confer permission to publish.

Responsibility and trust table
Container / boundary | Responsibility and constraint
Browser | Board/workspace presentation, drafts and conflict recovery; never authoritative for actor rights or persistence success.
CLI/service adapters | Validate external envelopes, authenticate actors, enforce request-origin protection for browser requests, translate core outcomes; CLI live writes use the host.
Shared Go core | Board commands, workflow/relationship rules, authorization decisions and explicit outcomes; no browser, transport, Git or supervisor dependencies.
Board persistence adapters | Commit/revision/integrity boundary selected by #0006; no cross-board transaction implied. Reject conflicting ownership of the same board storage identity.
Workspace host | Registry, board activation, aggregate health and lifecycle; preserve per-board permissions and partial failure. Cross-board links/operations require later explicit contracts.
Monitor/publisher adapters | Consume authorized sanitized activity or publication intent; expose separate save/publish states. Credentials remain in the owning runtime boundary, never browser bundles or public artifacts.

Ownership and lifecycle
An explicit launcher or service manager owns the host lifetime; closing a browser
window does not stop boards. A second launcher discovers the existing host or fails
clearly. Distinct hosts may own distinct boards, but never acquire the same storage
identity concurrently; aliases must not bypass ownership checks. Locking, stale-owner
recovery and host discovery details belong to later contracts.

Shutdown stops admission, settles or reports in-flight outcomes, persists worker
progress, then releases ownership. Worker restarts reconcile durable progress;
they never blindly replay user mutations. Monitor progress must preserve uncertain
intervals across host downtime, suppress only nonempty proven automation-only
activity, and keep prose/credentials out of alerts. Separate status/target/lock
records preserve each board's destination. Publishing failures do not roll back
local saves; shutdown reports pending publication truthfully.

Stopped-board maintenance uses the same Go core and storage adapters only after
exclusive ownership excludes the host and conflicting workers. Maintenance mode
does not silently start a live host. Core reuse means shared implementation, not
two independently writable authorities.

Alternatives and consequences
1. Recommended host plus supervised workers: efficient workspace startup and one
   browser contract, with independent board validation and worker recovery. A host
   crash can interrupt every hosted board; logical boundaries do not isolate memory
   corruption or process-wide failure. Validate resource fairness and restart recovery.
2. Separate service per board plus workspace aggregator: stronger crash/resource
   isolation, but more lifecycle, discovery and authorization coordination. Reconsider
   if measured host interference violates accepted budgets or exposure expands.
3. One process containing host and all background jobs: simplest packaging, but
   couples Git/network stalls and worker failures to interactive availability. Reject
   as the default for optional long-running external work.
