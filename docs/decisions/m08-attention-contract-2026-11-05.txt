1. Stable meaning and assignment
The stable category keys, in display order, are blocked, needsTerry and
readyForReview. Their fixed display names are Blocked, Needs Terry and Ready
for Review. Categories are board-policy metadata attached to lane identities.
They never derive from a lane label, its position, ticket number, card prose,
owner, priority, hierarchy or an unresolved relationship.

Blocked means work waits for an external condition which neither Terry nor Bot
can advance. Needs Terry means unfinished work requires a specific Terry input
or action. Ready for Review means the remaining step is Terry review/approval.
Normal prerequisite dependency alone does not imply Blocked. Pending review
alone does not imply Needs Terry. Users deliberately place cards in appropriate
lanes through existing card operations. Assignment makes no transition, grant,
approval, notification or automatic movement happen.

Each active lane belongs to at most one category. Each Blocked/Needs Terry set
contains zero through twelve active waiting-role lane IDs. Ready for Review
contains zero or one ID, which must be the one active review-role lane. Initial,
in_progress and completed lanes cannot be assigned. The two waiting categories
cannot overlap. Categories may cover no lanes. Multiple waiting lanes may share
a category so boards can keep distinct external/input queues. The existing
single protected review role preserves one approval handoff meaning.

Assignment lives in optional Workflow.attention, with this exact shape

  AttentionAssignments = {
    blocked: LaneId[], needsTerry: LaneId[], readyForReview: LaneId[]
  }

All three keys are required when attention is present. Each array is non-null,
sorted ascending by exact lane ID and duplicate-free. IDs must resolve in the
same complete candidate's active lanes, using its existing profile grammar.
Unknown keys, null, partial objects, label references, unknown/retired IDs,
wrong roles, overlap, unsorted/duplicate IDs and excessive cardinality refuse
as INVALID_INPUT. Validation never sorts, trims or silently repairs input.

Absent Workflow.attention means the implicit mapping at that policy version
  blocked=[], needsTerry=[], readyForReview=[current review-role ID].
The implicit default board uses the literal stable ID "Ready for Review".
Configured boards resolve their UUID review ID. Absent Workflow itself retains
the exact M07 implicit-default representation and this same implicit mapping.

An explicit empty array means that category is not configured. It is never a
known zero. A nonempty mapping with zero matching cards is known zero. Explicit
attention with all three arrays empty disables all three measures. Explicit
Ready for Review can be disabled because this field selects an Attention
measure, while the protected review lane and human approval flow remain fixed.
This gives explicit-empty one consistent meaning for all three categories.
Omission retains the accepted M07 review measure for existing boards. Explicit
attention matching the implicit mapping is still a configuration change because
its presence records a deliberate policy choice. Omitting attention in a later
full candidate deliberately restores implicit behavior and is a change. There
is no inheritance from the previous policy when the candidate omits the field.

2. One policy, one writer and exact historical interpretation
Reuse Workflow, workflow.edit, workflowPolicies and existing policyVersion.
There is no separate category revision, mutation command, grant or mutable
assignment table. A category-only or mixed edit submits one complete Workflow
candidate at current policyVersion+1. Existing M07 workflow show/preview/edit
entry points carry attention. Initial configured creation accepts this optional
field under the same validator at revision1. Untouched default creation still
omits Workflow and has implicit policy1.

This choice makes category/workflow races ordinary single-writer policy races.
One policy record describes labels, roles, transitions, ceilings and assignments
together. A separate category store would require cross-version pairing and
additional historical retention which this scope does not need.

Reuse exactly

- Existing body {opId,incarnation,target:null,expectedRevision,
  expectedCardRevision:null,input:{expectedPolicyVersion,workflow}}.
- POST /api/v1/boards/{boardId}/workflow/preview and its existing exact body.
- Result {workflowId,policyVersion}, workflow FactRef, workflow.edit activity.
- Current channel grant AND actor-kind edit ceiling, browser human and CLI
  automation attribution, native-owner separation and own-outcome authority.
- Existing board CAS, expectedPolicyVersion and original-resolution precedence.

Add attention to the existing Workflow descriptor and full-candidate equality.
Equality ignores only proposed revision, as M07 does. Presence versus absence
of attention matters. Exact NO_CHANGE creates no policy/card/activity counter,
and stores only its permitted durable refusal. Stale equal candidates still
refuse before equality. At most one competing old-revision policy/card/approval
mutation succeeds. Failures have no partial assignment/history effects.

Both category-only and mixed real first edits of implicit default1 enter the
M07 default profile and its strict current-card compatibility gate. An explicit
empty configuration is a real edit. WORKFLOW_INCOMPATIBLE retains legacy use,
opening and export boundaries. It does not repair old approvals. M07 exact
unchanged implicit candidates still avoid this first-edit gate.

Keep 4..16 lanes, 3..64 transitions, 65536-byte whole Workflow, 800000-byte whole
request, 128 retained policies and 8388608 canonical policy-array bytes. Category
bytes count in those existing bounds. No independent unbounded history is added.
Capacity includes implicit/version1. At capacity unchanged remains NO_CHANGE,
changed candidates refuse INVALID_INPUT. A new configured revision1 counts its
attention bytes in the same bounds.

Retiring an empty waiting lane requires removing its assignment in the same
candidate. Retiring a still-assigned or occupied lane refuses. Archived occupants
still prevent retirement. Every historical policy retains its exact assignment,
including absence. Retired IDs never return. Renames and array order changes do
not alter membership. Category-only changes leave every card revision, pin,
approval, snapshot, relation, comment, attachment and archived flag untouched.
Historical labels and categories resolve from the state's existing policy pin,
with omitted pin meaning1. Current counts and current lane presentation always
resolve current policy. Policy edits never repin old card states or snapshots.

M07 issuing-policy approval validation, human-only approval, terminal Completed,
current-pointer checks and source-owned blocking-prerequisite rules are unchanged.
Neither category assignment nor count proves an approval or satisfies a link.
Changing or disabling Ready for Review does not alter its protected lane/edges.
Stored grants and historical originals remain exact, including disabled grants
that exceed a later ceiling and valid refused foreign/retired-lane attempts.

4. Authoritative observations and wire shapes
Extend local.CatalogSnapshot using one withConfiguredRead/SQL read transaction.
Load and validate current complete policy, current grant/ceiling, identity,
revision, activity/coverage and all three counts inside that snapshot. Count
distinct committed current card identities where archived=false and lane is
in that category's resolved current set. Never count history, drafts, originals,
optimistic writes, archived cards or inherited child/linked-board state.

No mapping means {state:"not_configured",value:null}. A nonempty mapping returns
{state:"known",value:N}, including N=0. Counts are nonnegative safe integers.
The three sets are disjoint, so their known sum counts each card at most once.
Never manufacture a numeric zero after failed authorization/read/validation.

Use these exact additional DTOs, generated with the existing contract tooling

  AttentionContext = {
    policyVersion: PositiveSafeInteger,
    workflowId: UUID | null,
    profile: "default" | "configured",
    source: "implicit" | "explicit",
    assignments: AttentionAssignments,
    lanes: {id:LaneId,label:WorkflowLabel,role:"waiting"|"review"}[]
  }
  BoardAttention = {
    apiVersion:1,boardId:UUID,incarnation:UUID,revision:SafeInteger,
    attentionContext:AttentionContext,attention:CatalogAttention

lanes contains exactly the assigned lane IDs once, sorted ascending by exact ID,
with labels/roles from the same current policy. workflowId is null only for
implicit default1. profile defaults to configured when Workflow.profile is
omitted. source describes attention-field presence, not profile. Policy/version
and lane details are sufficient for category explanation without exposing cards
or entire retained history in the catalog. Unknown fields/null alternatives not
listed here refuse at strict decode boundaries.

5. Ordering and presentation
Keep existing catalog order by last committed card activity descending, null
last. For equal non-null times use fresh known aggregate Attention descending.
For this tie only, a fully observed not_configured component contributes0.
A valid fresh observation with all three disabled therefore has ranking sum0.
Fresh aggregate ranks before stale/unknown aggregate. Two stale/unknown values
do not receive invented numeric comparison. Then keep current case-folded board
label, projectKey and boardKey ascending. When both activity times are null,
keep the existing label/key fallback. Do not compare different-board revisions.

workflow.edit advances board revision and policy activity but never
lastCardActivity. A category change can alter the aggregate tie-break, which is
expected. It cannot masquerade as a newer card event. Category display order is
fixed Blocked, Needs Terry, Ready for Review regardless of JSON member order.

Render known0 as 0, not_configured as Not configured, stale values explicitly
as stale with their observation age, and unknown as Unavailable. Never hide the
distinction using a bare dash or sum displayed as an authoritative total. Show
current category source, stable lane IDs/roles and policy context in editor/detail
views. Preserve selected board/editor DOM, focus, filters, pins, route and private
drafts during workspace refreshes and equal-ticket member changes.
