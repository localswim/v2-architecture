1. Types and ordinary reciprocal use

2. Atomic create with owned links AND parent
Use normal card.create input title/description/explicit priority/owner, optional
parent:prerequisite and relationships to existing peers. One card/ticket, parent
and all Link facts/current refs appear at one board revision; source starts at
normal create revision. Result is exactly cardId, compact/full ResultRefs one card.
Read fresh BoardRead to discover link IDs. Confirm no peer content mutation.
For every member position, substitute one invalid foreign/incarnation/missing/self
target, unknown kind, duplicate semantic entry or invalid parent: no partial card,
ticket allocation, links, refs, prior snapshot or board/activity advance. Distinguish
durable original refusal from pre-dispatch structural refusal; ledger evidence may
exist without committed card state. A proposed two-new-card batch is unsupported.

3. Whole OWNED set replacement
Seed outgoing blocking+informational+reference, incoming reference+related from
other owners, and an inactive historical link. card.edit relationships only retains
identical matching IDs, deactivates removed outgoing facts and allocates new IDs
for additions at one owner revision. Incoming facts remain byte-identical except
their derived display may refresh from the new board revision. Reverse-related
ownership is not stolen; conflicting ownership proposal refuses. Reordering an
equal set returns durable NO_CHANGE without snapshots/activity/card revision.
[] clears all owned active kinds including informational; incoming remains visible.
Null relationships or mixed fields (including parent/archive/priority) refuse.
Inactive historical IDs never resurrect. Completed source refuses even equal/clear;
unfinished archived source works under normal edit permission. Archived/Completed
peer targets remain legal without a peer revision or approval change.

4. Graphs, bounds and concurrent admission
blocking A->B->C refuses added C->A (BLOCKING_CYCLE); duplicate A->B->C refuses
C->A (DUPLICATE_CYCLE). Refuse two outgoing duplicate targets. Related/reference/
informational cycles are legal; a hierarchy edge and opposing link alone are legal.
A batch whose individually plausible additions close a cycle refuses as a whole;
validate against final proposed set after intended removals. Existing legacy
blocking cycles/external facts survive unrelated operations and6->7 conservation;
new edges must not introduce a cycle, and traversal must terminate. Clear/removal
repairs are allowed. Synthetic controlled100/101-entry arrays prove the batch cap;
this does not bound existing incoming/board sets or truncate reads.
Two windows use the same expected board revision for conflicting additions or
replacement: at most one commits; the other retains input with original conflict
evidence, never automatic retry. Capture all allocations/counters/full records.

5. Canonical, identity and authority compatibility
Golden omitted-field card.create/edit and legacy link.add targetCardId fingerprints
and complete canonical bytes stay equal after new decoders/refreeze/export/restore.
Modern exact-target link.add and relationships are distinct originals. Empty[] is
preserved as intentional; null refuses. Input array order is retained in canonical
bytes even where semantic set equality yields NO_CHANGE. Freeze/browser/archive
must agree; no target:null or relationships:null padding in old intents.
Test wrong board/member/incarnation, colliding ticket, missing peer, sourceCompleted,
forbidden actor and revoked authority, stale board/source revisions and foreign
linkId/owner. No target/permission guessed from labels, assignment or inverse view.
Legacy equal add and inactive/missing remove keep their admitted refusal codes.

6. Failure, private input, original recovery and focus
